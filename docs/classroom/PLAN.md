# LUNARIS Classroom: build plan and contracts

Owner: the technical-director (TD) session. Written 11 November 2026.

This is the working plan for the Chulalongkorn University Innovative Award 2570 entry
(deadline **27 November 2026, 16:30**; the team submits on the 26th). The background and
the evidence are in `reports/LUNARIS Thai secondary education proposal.md`. Where this
file and the proposal disagree, this file wins.

The working rules in `docs/TASKS.md` section 1 apply to every session here: your own
branch and draft PR, edit only the paths you own, `npm run check` green before you ask
for review, and the PR body lists each acceptance criterion with its evidence.

## 1. What is being built

The entry is a **six-period ม.3 learning-activity set** with LUNARIS inside it. Three
layers:

1. **The teaching kit** (documents, Thai): lesson plans, three worksheets, a decision memo
   template, a test. This is what the judges score.
2. **Classroom mode** (`/learn`): a guided route through the same data.
3. **The existing Explorer** (Overview, Illumination & Earth, Terrain, Compare, Data,
   About): the open-ended instrument, in the same light theme and in Thai (D11, D14).

The entrants are upper-secondary students with an advisor teacher. The software and the
science core were written largely with AI assistance; the entry says so.

## 2. Decisions (D10–D13)

- **D10: lessons never call the live API.** A class of 30–40 students opening the page
  together cannot wait for a sleeping free-plan server. Every number a lesson shows comes
  from a **lesson pack**: JSON files generated once from the real science core, committed,
  and served as static files with the web app. The pack records the code commit and the
  dataset checksums it was built from. The Explorer keeps using the live API.
- **D11: Thai by default across the app, with an English switch.** (Widened on 11
  November at the advisor's request; the first version covered the lesson route only.)
  All interface text reads from a typed message catalogue with `th` (default) and `en`.
  No i18n framework dependency. The lesson route and the shell come first (K-03), the
  Explorer pages after the light theme (K-13). **One exception:** the method, source and
  limitation text inside each value's evidence is generated by the science core and the
  API and stays in English for now, shown under a Thai heading that says so. A wrong
  translation of a method is worse than none.
- **D12: phases are geocentric and labelled as such.** The Earth-view camera looks at the
  Moon from the direction of Earth's centre, north up. It does not show the tilt or the
  rise and set times for an observer in Thailand. The readout says so. Moonrise for a
  Thai observer is a later task (K-07) and is not claimed before it exists.
- **D13: claim only what the software does.** Tides are taught unplugged until K-08
  exists. The verb in the ม.3 indicators is "construct a model", so periods 1–2 use a
  physical lamp-and-ball model; the software does not replace it.

- **D14: a light, roomier look for the whole app.** The advisor asked for larger text
  and a lighter interface in keeping with a learning tool. The app moves from the
  dark mission-control theme to a light theme: off-white surfaces, dark text, one or two
  warm accents, sans-serif for prose and labels (monospace for numbers and codes only),
  more spacing, 14 px minimum body text in lessons. The Moon globe, the terrain scene and
  the sky chart keep a dark background as framed "windows into space". All colour comes
  from the tokens in `apps/web/src/app/globals.css`; no component hard-codes a colour.
  Contrast meets WCAG AA and the existing contrast test is updated to prove it. **Two
  sample screens go to the team for the advisor's approval before the rest is
  converted.**

## 3. Contracts

### L1: Moon phase series (science core + API)

New in the science core, mirroring the existing Sun direction series, then exposed as
`GET /api/v1/ephemeris/moon-phase?start=…&end=…&step_s=…`.

Each sample:

| Field | Meaning |
|---|---|
| `epoch_utc` | ISO 8601 UTC |
| `earth_direction_moon_me` | unit vector, Moon centre to Earth centre, `MOON_ME`, apparent (same aberration convention as the Sun series) |
| `subearth_latitude_deg`, `subearth_longitude_deg` | sub-Earth point; longitude east in [0, 360) |
| `phase_angle_deg` | Sun–Moon–Earth angle at the Moon's centre |
| `illuminated_fraction` | fraction of the disk lit as seen from Earth's centre, `(1 + cos(phase angle)) / 2` |
| `elongation_deg` | Sun–Earth–Moon angle at Earth's centre |
| `waxing` | true while the Moon's geocentric ecliptic longitude leads the Sun's by 0–180° |

The series carries `evidence` (kind `model`) like every other result: method, sources
with checksums, limitations (geocentric, not topocentric; no libration-dependent
brightness; no earthshine).

**Validation is required and must be independent.** Compare new-Moon, first-quarter,
full-Moon and last-quarter instants for 2027 against a published source (JPL Horizons if
reachable from the session, otherwise a published almanac) and record the measured
differences in `docs/SCIENCE.md`. If no independent source can be reached, say so in the
PR and label the series `unvalidated` in its evidence. Do not invent a tolerance.

### L2: Lesson pack

Generated by `scripts/build_lesson_pack.py` into `apps/web/public/lesson-pack/v1/`. The
script calls the API **services in process** (no HTTP server) so the pack is exactly what
the API would return.

- `manifest.json`: pack version, `generated_at_utc`, code commit, the window of each
  file, every source dataset's id and SHA-256, and the SHA-256 and byte size of each pack
  file.
- One JSON file per API response the lessons need. Each file is the **unmodified response
  body** of the endpoint it stands for, so the existing response types and components
  work on it:
  - Sun direction series and Moon phase series (L1) over one full lunation in 2027,
    hourly. The pack names the lunation.
  - For the demo trio (Peak near Shackleton, Connecting ridge, Malapert massif): site
    record, horizon mask, illumination and Earth-visibility result over the same
    lunation, and the 2027 comparison with its summary (no profile, and each of the three
    profiles).
  - One permanently shadowed example if the catalogue has a site whose computed sunlit
    fraction is 0 % over the window; otherwise leave it out and say so in the PR.
- Budget: the whole pack **under 3 MB uncompressed** if possible; report the measured
  size. Downsample series rather than exceed it, and record the step in the manifest.
- A test loads the committed pack, checks every file against the manifest hashes and
  validates each file against its response model.

### L3: Lesson data access (web)

`/learn` reads the pack through one module, `apps/web/src/lib/lesson/pack.ts`, that
returns the same typed objects the API client returns. Lesson components must not import
`lib/api/client` or `lib/api/queries`. An end-to-end test runs the whole lesson route
with the API **not started** and asserts no request leaves for the API host.

## 6. Wording rules for the lesson route and the kit

- Thai astronomy terms follow the Royal Society dictionary and the IPST ม.3 textbook. A
  term the session is unsure of goes in `docs/classroom/kit/glossary.md` with a
  `ตรวจสอบ` (to check) mark; the team reviews that file.
- Phase names used in the readout, pending the team's review: จันทร์ดับ, ข้างขึ้น (เสี้ยว),
  ข้างขึ้น (ครึ่งดวง), ข้างขึ้น (ค่อนดวง), จันทร์เพ็ญ, ข้างแรม (ค่อนดวง), ข้างแรม (ครึ่งดวง),
  ข้างแรม (เสี้ยว). The lunar-calendar day number (ค่ำ) is **not** computed: it is a
  calendar convention and can differ from the astronomical phase by a day.
- No statistic from the proposal goes into the kit or the entry form until its source has
  been opened and checked. The proposal's own "verify before 27 November" table lists the
  doubtful ones.
- Every number a student sees keeps its evidence label. In a lesson, show the one label
  that matters for the step and fold the rest away.
